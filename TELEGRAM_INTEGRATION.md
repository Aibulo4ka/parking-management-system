# Telegram-интеграция: архитектура и сценарии

Документ описывает интеграцию системы управления парковкой с Telegram Bot API в качестве дополнительного канала уведомлений. Цель — выполнение требования курсовой по дисциплине «Проектирование интеграционных решений» (интеграция с внешним API) и одновременно практическая фича: пользователь получает события по своим бронированиям прямо в Telegram, без email-почты.

Бот: [@parkovkatorbot](https://t.me/parkovkatorbot) («Парковкатор»).

---

## 1. Что было до интеграции и что добавлено

**До:** в `notification_service` была заглушка — все «уведомления» писались в лог backend-контейнера в виде «EMAIL: To: …, Subject: …». Реального канала доставки не было.

**Стало:**

- `notification_service` шлёт сообщения и в email-лог (формально, на будущее), **и** в Telegram, если у пользователя привязан аккаунт.
- Пользователь может через UI на сайте сгенерировать одноразовый токен, нажать ссылку и привязать свой Telegram к учётной записи.
- Фоновый воркер раз в минуту проверяет ближайшие брони и отправляет напоминания за 30 минут до начала.

Интеграция реализована как **отдельный канал**: Telegram не заменяет email, а добавляется к нему. Если бот не настроен или у юзера нет привязки — система ведёт себя как раньше, ничего не ломается.

```
                                               │  └──────┬────────┘  │                          /start <TOKEN>

                                               │  ┌──────▼────────┐  │                                │

                                               │  └───────────────┘  │                          │   юзер    │

                                                  ┌──────▼──────┐
                                                  │ PostgreSQL  │
                                                  └─────────────┘
```

Ключевые слои:

- **`app/services/telegram_service.py`** — тонкая async-обёртка над Bot API (`sendMessage`, `getUpdates`, `getMe`). С ретраями (3 попытки) и коротким таймаутом (8с), потому что сеть до `api.telegram.org` бывает flaky.
- **`app/services/telegram_polling.py`** — фоновый воркер long-polling, принимает входящие апдейты от Telegram. Сейчас обрабатывает только `/start <TOKEN>` (привязка аккаунта).
- **`app/services/reminder_worker.py`** — независимый фоновый цикл, раз в `REMINDER_POLL_INTERVAL_SECONDS` ищет брони, которым пора напомнить о начале.
- **`app/services/notification_service.py`** — единая точка отправки уведомлений. Каждый метод `send_*` принимает опциональный `telegram_chat_id` и при наличии шлёт HTML-сообщение в чат.
- **`app/api/endpoints/telegram.py`** — REST API для UI: генерация link-token, проверка статуса, отвязка.

## 4. Сценарий: привязка Telegram к аккаунту

```
[Пользователь]          [Frontend]          [Backend]            [Telegram]
      │                     │                   │                    │
      │  заходит в профиль  │                   │                    │
      │ ─────────────────▶ │                   │                    │
      │                     │   GET /status     │                    │
      │                     │ ─────────────────▶│                    │
      │                     │   {linked: false} │                    │
      │                     │◀───────────────── │                    │
      │  «Подключить TG»    │                   │                    │
      │ ─────────────────▶ │                   │                    │
      │                     │ POST /link-token  │                    │
      │                     │ ─────────────────▶│                    │
      │                     │                   │ создаёт TLT,       │
      │                     │                   │ TTL=10мин          │
      │                     │ {deep_link, ...}  │                    │
      │                     │◀───────────────── │                    │
      │  ссылка t.me/...    │                   │                    │
      │◀─────────────────── │                   │                    │
      │  открывает в TG     │                   │                    │
      │ ─────────────────────────────────────────────────────────▶ │
      │                     │                   │  getUpdates        │
      │                     │                   │◀───/start <TOKEN>──│
      │                     │                   │ валидирует TLT,    │
      │                     │                   │ ставит             │
      │                     │                   │ customers          │
      │                     │                   │ .telegram_chat_id, │
      │                     │                   │ used=true          │
      │                     │                   │  sendMessage       │
      │                     │                   │ ─── «Готово» ────▶ │
      │  получает «✅ Готово»                                          │
      │◀─────────────────────────────────────────────────────────── │
```

Ключевые детали:

- Токен одноразовый, **`secrets.token_urlsafe(24)`** — криптографически стойкий, не угадывается.
- При генерации нового токена старые неиспользованные токены того же юзера удаляются (`endpoints/telegram.py:48-53`) — защита от накопления мусора и от попыток reuse.
- Сам chat_id никогда не передаётся через URL/Frontend — он попадает в БД только из апдейтов Telegram, которые приходят с авторизованной стороны (Bot API).
- Один Telegram-чат не может быть привязан к двум разным аккаунтам — это проверяется в `telegram_polling._consume_link_token` атомарно в одной транзакции (см. `telegram_polling.py:166-173`).
- Если токен истёк, или уже использован, или не найден — бот отвечает текстовой ошибкой, а БД не трогается.

Отвязка: `DELETE /api/telegram/link` сбрасывает `telegram_chat_id = NULL` у юзера и чистит его неиспользованные токены.

## 5. Сценарий: автоматические уведомления о событиях

Сейчас система шлёт **пять** разных типов сообщений. Все они срабатывают автоматически в момент бизнес-событий — никаких ручных вызовов не требуется.

### 5.1. Подтверждение бронирования

**Триггер:** `POST /api/bookings` создаёт бронь, списывает деньги с баланса. Сразу после `db.commit()` вызывается `notification_service.send_booking_confirmation`.
**Call-site:** `app/api/endpoints/bookings.py:256`.
**Сообщение:**

```
✅ Бронирование подтверждено
№ 12345678
Зона: Центральная парковка, место A-12
С 25.05.2026 14:00 до 25.05.2026 18:00
```

### 5.2. Напоминание о брони

**Триггер:** фоновый `reminder_worker` каждые 60 секунд ищет брони, у которых:
- `status IN ('pending', 'confirmed')`
- `reminder_sent_at IS NULL` (ещё не напоминали)
- `start_time` попадает в окно `(now, now + REMINDER_LEAD_MINUTES]` (по умолчанию 30 минут)
- `customers.telegram_chat_id IS NOT NULL`

Найденным броням рассылает сообщение и проставляет `reminder_sent_at = now()`.
**Call-site:** `app/services/reminder_worker.py:88`.
**Сообщение:**

```
⏰ Скоро начало брони
Зона: Центральная парковка, место A-12
Начало: 25.05.2026 14:00
```

### 5.3. Въезд (начало парковочной сессии)

**Триггер:** `POST /api/sessions` фиксирует въезд автомобиля, помечает место занятым.
**Call-site:** `app/api/endpoints/sessions.py:246`.
**Сообщение:**

```
🚗 Въезд зафиксирован
Зона: Центральная парковка, место A-12
Авто: А123БВ77
Время: 25.05.2026 14:05
```

### 5.4. Выезд (завершение сессии)

**Триггер:** завершение сессии — пересчёт длительности и стоимости, создание платежа (если есть долг сверх предоплаты).
**Call-site:** `app/api/endpoints/sessions.py:570`.
**Сообщение:**

```
🅿️ Выезд зафиксирован
Зона: Центральная парковка, место A-12
Авто: А123БВ77
Длительность: 4ч 0мин
К оплате: 240.00 ₽
```

### 5.5. Платёж

**Триггер:** успешная оплата (`payment.status == "completed"`).
**Call-site:** `app/api/endpoints/payments.py:345`.
**Сообщение:**

```
💳 Платёж прошёл
Сумма: 240.00 ₽
Способ: Банковская карта
№ платежа: 99887766
```

### Важные архитектурные свойства

- **TG-отправка идёт после `db.commit()`** — если Telegram упал, бизнес-логика уже зафиксирована, бронь/сессия не откатится. То есть TG — это «best-effort» канал, не часть транзакции.
- **Все `send_*` ловят исключения внутри** (try/except в каждом методе `notification_service`) и возвращают `False`. API-эндпоинт всегда отдаст 200/201 пользователю, даже если TG недоступен.
- **Условная отправка:** если у юзера `telegram_chat_id IS NULL`, метод `_send_telegram` (`notification_service.py:250`) тихо возвращается. Привязка обязательна для уведомлений, но её отсутствие не ломает ничего.
- **Все даты приводятся к Москве** (UTC+3, без DST) в форматтере `_fmt_dt` — пользователь видит время в своём часовом поясе, а БД хранит всё в UTC.

## 6. Reminder worker: подробнее

Это единственный по-настоящему асинхронный канал — он не привязан к запросу пользователя.

Жизненный цикл:

1. На старте FastAPI (lifespan, `app/main.py:24-27`) воркер запускается, если `REMINDER_ENABLED=true`.
2. В цикле: `_tick()` → ждать `REMINDER_POLL_INTERVAL_SECONDS` → `_tick()` → ...
3. Каждый `_tick()` открывает свою сессию БД (через `AsyncSessionLocal`), ищет брони по условиям выше, шлёт уведомления, проставляет `reminder_sent_at`, коммитит.
4. На остановке (lifespan exit) воркер получает `_stopping.set()` и `cancel()`.

Свойства:
- **Идемпотентность:** благодаря `reminder_sent_at IS NULL`-фильтру одна бронь получит максимум одно напоминание, даже если воркер перезапустится.
- **Отзывчивость к остановке:** между тикaми используется `asyncio.wait_for(self._stopping.wait(), timeout=...)` вместо обычного `asyncio.sleep` — `Ctrl+C` сразу прерывает сон.
- **Изоляция ошибок:** один проблемный тик не валит весь воркер — ошибки логируются и цикл продолжается.

## 7. Long polling vs Webhook: обоснование выбора

Telegram Bot API поддерживает два режима получения апдейтов:

| | Webhook | Long polling |
|---|---|---|
| Нужен публичный URL | Да (HTTPS, валидный сертификат) | Нет |
| Зависимость от внешних сервисов | Domain + TLS-сертификат | Только сеть до `api.telegram.org` |
| Сложность для локальной разработки | Высокая (ngrok/туннели) | Минимальная |
| Подходит для production-нагрузки | Лучше | Хуже (один запрос держит соединение) |
| Простота отладки | Сложнее | Проще |

**Выбран long polling**, потому что:
- Проект курсовой — запускается локально, у пользователя нет публичного домена и TLS-сертификата.
- Нагрузка ничтожная — один пользователь, несколько событий в день.
- Все остальные плюсы (нет внешних зависимостей, проще отладка) перевешивают.

Реализация — `telegram_polling.py:75`: `getUpdates` с `timeout=25` секунд (`long-poll`). Если апдейтов нет — Telegram держит соединение и возвращает пустой массив через 25с, цикл продолжается. Если апдейты есть — возвращает сразу.

## 8. Устойчивость к flaky-сети

Сеть до `api.telegram.org` бывает нестабильной (особенно в РФ). Реализованы три уровня защиты:

1. **Ретраи на отправке.** `TelegramService.send_message` делает до 3 попыток с задержками `0.5s` и `1.5s` (`telegram_service.py:20-22`) и коротким timeout (`8s`). Этого хватает на короткие сетевые сбои.
2. **Не убивающий воркер цикл `get_me`.** На старте polling-воркер проверяет связь через `getMe`. Раньше при первой ошибке воркер падал навсегда — теперь он ретраит с бэкоффом `5s` (`telegram_polling.py:62-79`) до тех пор, пока не подключится или пока его не остановят.
3. **Бэкофф при ошибках getUpdates.** Если `getUpdates` упал — воркер ждёт `5s` и пробует снова, не сжигая CPU и не спамя в лог.

Это позволяет включать VPN/прокси на лету: воркер сам поднимется, когда сеть восстановится, без рестарта backend.

## 9. REST API для UI

Все эндпоинты в `app/api/endpoints/telegram.py`, подключены под `/api/telegram/`.

### `POST /api/telegram/link-token`

Авторизованный запрос. Создаёт одноразовый токен для текущего юзера.

**Ответ:**
```json
{
  "token": "S0meRand0mTok3n...",
  "deep_link": "https://t.me/parkovkatorbot?start=S0meRand0mTok3n...",
  "expires_at": "2026-05-25T14:30:00Z",
  "ttl_seconds": 600
}
```

Ошибки:
- `400` — у юзера уже есть привязка (нужно сначала отвязать).
- `503` — бот не сконфигурирован на сервере.

### `GET /api/telegram/status`

Авторизованный запрос. Возвращает текущее состояние привязки.

**Ответ:**
```json
{
  "linked": true,
  "telegram_chat_id": "1160248718",
  "bot_username": "parkovkatorbot"
}
```

### `DELETE /api/telegram/link`

Авторизованный запрос. Отвязывает Telegram от текущего аккаунта (сбрасывает `telegram_chat_id`, чистит неиспользованные токены).

## 13. Что осталось за рамками

Сознательно не делалось:

- **Команды бота** `/mybookings`, `/status <id>` — расширение polling-обработчика. Технически тривиально, но за рамками задачи: интеграция курсовой о «канале уведомлений», а не о «втором интерфейсе системы».
- **Mini App / inline-keyboard** — кнопки в сообщениях. Аналогично — overkill для курсовой.
- **Webhook-режим** — рассмотрен, отклонён по причинам выше.
- **Rate-limiting на отправке** — у Telegram есть лимит ~30 сообщений в секунду на бота. При текущей нагрузке (1 юзер ≪ 30 msg/s) это не проблема. На реальном production нужно было бы добавить очередь и дросселирование.

## 14. Известные особенности окружения

- **Сеть до `api.telegram.org` из Docker-контейнера** в РФ часто требует VPN. На macOS Docker Desktop в host-networking-режиме всё равно живёт в собственной VM с изолированным сетевым стеком — системный VPN на маке не пробрасывается. Самое надёжное в этом случае — либо настроить VPN внутри контейнера, либо запускать backend на хосте, либо использовать VPN, который покрывает и Docker.
- **Дрейф схемы БД vs модели:** alembic autogenerate видит расхождения между моделями SQLAlchemy и реальной схемой БД (TIMESTAMP vs DateTime(timezone=True), имена индексов). Миграция `664ec4d0ef9b` чистилась вручную. При следующих autogenerate-миграциях мусор всплывает снова — нужно чистить руками или сделать отдельную миграцию-выравниватель.

## Кратко

- Один canonical путь уведомлений: бизнес-событие → `notification_service.send_*` → email-лог + (опционально) Telegram.
- Привязка аккаунта через одноразовый URL-safe токен в БД (TTL 10мин), сам chat_id попадает в БД только из верифицированных Telegram-апдейтов.
- 5 типов событий: booking confirmation, reminder, session start, session end, payment. Из них 4 синхронные после `db.commit()`, 1 (reminder) — фоновый воркер.
- Long polling вместо webhook — нет публичного URL, проще отладка.
- TG никогда не ломает бизнес-логику: исключения проглатываются, неудачная отправка не откатывает транзакцию.
- 134 теста, всё зелёное.
